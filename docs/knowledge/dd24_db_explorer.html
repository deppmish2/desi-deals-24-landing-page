deal_price_history
Immutable, append-only daily price snapshots. The foundation of Phase 2's Real Savings rating system. One row per (crawl_date, store_id, product_url) — the UNIQUE constraint guarantees no double-counting.
Append-only — never deleted Powers Phase 2 baseline No FK to deals
Key Columns
ColumnTypeNotes
crawl_dateTEXTe.g. "2026-04-15". Part of UNIQUE(crawl_date, store_id, product_url).
store_idTEXT FK→ stores(id). No cascade. Denormalised — store identity at snapshot time.
product_urlTEXTStable per-product identifier. Also the join key back to deals — no FK, just a string match.
sale_priceREALPrice on this day.
price_per_kgREALNormalised at write time for cross-weight comparison.
is_dealINTEGER⚠ Critical for Phase 2. 1 = product was on promotion that day. Added via always-run migration. Baseline must exclude is_deal=1 rows.
crawl_run_idTEXT FK→ crawl_runs(id). No cascade.
Phase 2 Baseline Logic
-- 90-day non-deal baseline per product SELECT product_url, median(sale_price) AS normal_price_baseline FROM deal_price_history WHERE is_deal = 0 AND crawl_date >= date('now', '-90 days') GROUP BY product_url -- Hard override rule: -- if current_price > baseline → Weak, regardless of gap
Risks & Notes
⚠ is_deal Classification Quality If is_deal was defaulted to 0 on rows that were actually promotional prices (e.g. during backfill), your Phase 2 baselines are contaminated. Run: SELECT is_deal, COUNT(*) FROM deal_price_history GROUP BY is_deal — before Phase 2 ships.
⚠ No FK to deals The join to deals is on product_url — a string match, not a relational guarantee. If a store changes a product URL, history for that product becomes unreachable — orphaned rows with no reconnection path.
⚠ Growth & Query Performance 27 stores × ~500 products × 365 days ≈ 5M rows/year. The Phase 2 baseline query (median over 90 days, grouped by product_url) will get expensive. Add a composite index on (product_url, crawl_date, is_deal) before Phase 2 ships.
⚠ 90-Day Minimum Data Required Phase 2 is not viable until this table has 90 days of clean history. Verify when population started and whether any crawl failures created gaps in the timeline.
entity resolution
canonical_products
Central entity-resolution hub. ~90 unique product identities. Every raw deal eventually resolves to a row here — or fails and enters the review queue. The entire cross-store comparison engine depends on this table being clean.
PK: id (TEXT slug) ~90 canonical products Manual rename cascades
Three Roles
01
Matching Target
canonical_name is what the fuzzy matcher scores incoming deal names against. Quality here = resolution rate everywhere.
02
Price Anchor
batchGetRealSavings() groups deals by canonical_id to compute cross-store medians. Bad canonicals = bad Real Savings ratings.
03
User Identity
What appears in shopping lists, price alerts, and Phase 3 basket comparison. The user-facing product name.

Risks & Notes
⚠ TEXT Slug PK — Rename is Dangerous No ON UPDATE CASCADE. A canonical_id rename requires manually updating deals, deal_mappings, list_items, price_alerts, entity_resolution_queue. Miss one table and you get silent orphans. No migration script exists for this yet.
⚠ Phase 2 Minimum Deal Count Threshold If a canonical has only one deal mapped to it, the "cross-store median" is just that price — no comparison possible. Define and enforce a minimum deal count before a canonical is eligible for Real Savings ratings.
⚠ Slot Schema Has No Write Validation The nested array structure [["heera"]] vs [["soan"],["papdi"]] is non-obvious. A flat array instead of nested, or a null, will cause decomposeCanonical() to produce wrong token decompositions silently. Add validation on write.
ℹ Coverage Gap With ~90 canonicals across 27 stores, any unmapped deals sit as canonical_id=NULL on deals or in entity_resolution_queue. That gap directly limits Phase 2 and Phase 3 at launch.
entity resolution
deal_mappings
The bridge that makes cross-store price comparison possible. Maps every raw scraped deal to its canonical product identity. Without clean data here, every deal is an island — batchGetRealSavings() produces garbage.
PK: (deal_id, canonical_id) Powers batchGetRealSavings() No index on deal_id
Key Columns
ColumnTypeNotes
deal_idTEXT FK→ deals(id) CASCADE. If a deal is hard-deleted, this row disappears silently.
canonical_idTEXT FK→ canonical_products(id) CASCADE. Indexed — this is the join key for batchGetRealSavings().
match_methodTEXTexact | fuzzy | manual | slot. Tells you how much to trust the mapping.
match_confidenceREAL (0–1)Score from matching pipeline. 1.0 for exact/manual. 0.82–0.89 band is fuzzy-mapped but arguably not trustworthy.
verified_atDATETIMENULL = auto-matched. Set = admin-confirmed. Only verified rows should drive Phase 2 ratings.
How a Row Gets Written — Pipeline
raw deal name → normalise() Layer 1: strips units, qualifiers, synonyms → fuzzyMatch() ≥ 0.82 → INSERT here (method='fuzzy') 0.60–0.81 → Layer 3 → Claude Haiku YES → INSERT (confidence=0.90, method='ai') UNSURE → entity_resolution_queue NO → new canonical_products row created
Risks & Notes
⚠ No Unique Constraint on deal_id The PK is (deal_id, canonical_id). A single deal can technically map to multiple canonicals. That would double-count it in batchGetRealSavings() and corrupt reference prices. Verify this hasn't happened in production.
⚠ Confidence Gap 0.82–0.89 The pipeline writes fuzzy matches at ≥0.82 with method='fuzzy'. The entity_resolution_queue threshold is 0.90. Rows between 0.82–0.89 are mapped but unreviewed — they're the highest false-positive risk band. Check the actual error rate here.
⚠ Missing Index on deal_id The only index is on canonical_id. Queries looking up "what canonical does this deal map to?" — which happen during crawl updates — do a full table scan. Add idx_deal_mappings_deal_id.
ℹ deals.canonical_id Sync Writing a mapping row here must also update deals.canonical_id. These two must stay in sync — a mapping without the corresponding deals update is a silent bug that breaks deal card display.

entity_resolution_queue
Admin review queue for deals that couldn't be auto-matched (confidence < 0.90). A debt accumulator — every failed resolution adds a row. Backlog size here directly measures your coverage gap.
PK: INTEGER AUTOINCREMENT Status: pending | confirmed | dismissed Debt accumulator
Key Columns
ColumnTypeNotes
deal_idTEXT FK→ deals(id) CASCADE. Row disappears if deal is deleted.
suggested_canonical_idTEXT FK→ canonical_products(id) SET NULL. Best fuzzy guess — the thing to confirm or reject.
confidenceREALScore of the suggestion. Rows with confidence 0.60–0.89 come from fuzzy miss; lower = likely new product.
raw_nameTEXT NOT NULLOriginal deal name from store. What the admin sees.
normalised_nameTEXTStored at enqueue time. Re-derived live on GET for display.
statusTEXT'pending' default. confirmed = write to deal_mappings. dismissed = skip.
store_idTEXT FK→ stores(id) SET NULL. Added via always-run migration. Context for the admin reviewer.
categoryTEXTAdded via always-run migration. Used for queue filtering in admin UI.
Risks & Notes
⚠ Uncapped Growth Rows only leave this table when an admin confirms or dismisses them. With no automated resolution for pending rows, every crawl with new products adds more. What's the current pending backlog? That number is your effective unmapped product count.
⚠ Admin Bottleneck for Phase 2 Phase 2 Real Savings ratings require canonical mappings. Any product stuck here is ineligible for ratings. Systematic backlog review before Phase 2 launch is a prerequisite, not optional.
