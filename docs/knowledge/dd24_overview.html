Reconciling Deals (deals table)
reconcileStoreDeals() compares incoming scraped URLs against existing rows in the deals table.
SituationActionNotes
New URL INSERT new row, is_active=1 Fresh deal seen for the first time
Price changed UPDATE price fields, keep is_active=1 URL matched but sale_price or discount differs
Same price Touch updated_at, keep is_active=1 No data change; only timestamp refreshed
Removed SET is_active=0 URL not returned by scraper this run
Soft-delete pattern

Deals are never hard-deleted. is_active=0 is the soft-delete pattern. Historical price data and canonical mappings are preserved. A deal that reappears simply gets is_active=1 again on the next crawl.

Deduplication key

deals.product_url is the dedup key scoped per store. Two different stores can have the same product URL without conflict because each adapter belongs to exactly one store_id.

Daily Price Snapshots (deal_price_history)
Provides the 90-day historical baseline required by the Real Savings engine.
Why this table exists

The deals table only keeps the current price. To compute whether today's price is genuinely low, Real Savings needs a reference baseline — the median normal price over the past 90 days. deal_price_history stores one row per deal per crawl day, giving that time series.

Write pattern — delete-then-insert

Each crawl run calls recordStoreHistory(storeId). It deletes today's existing rows for that store, then re-inserts fresh rows from current active deals. This ensures idempotency — rerunning a crawl on the same day produces exactly one row per deal, not duplicates.

is_deal flag

is_deal=1 — the product was on sale during this snapshot (has a discount).
is_deal=0 — inserted in Pass 1 (post-crawl) for priority products at their normal price, using INSERT OR IGNORE to preserve any is_deal=1 record if it already exists that day.

This two-pass approach captures both "on sale" and "not on sale" price points, enabling a clean normal-price baseline even for products that are sometimes discounted.

Baseline SQL (Real Savings)
SELECT dm.canonical_id, MEDIAN(dph.price_per_kg) AS baseline_price_per_kg, COUNT(*) AS observation_count FROM deal_price_history dph JOIN deals d ON dph.deal_id = d.id JOIN deal_mappings dm ON d.id = dm.deal_id WHERE dph.snapshot_date >= DATE('now', '-90 days') AND dph.is_deal = 0 -- normal-price days only AND dph.price_per_kg IS NOT NULL GROUP BY dm.canonical_id HAVING COUNT(*) >= 3 -- minimum 3 observations required
Pass A — Slot-based Auto-mapping
Fast, high-precision matching using pre-compiled slot regex patterns from canonical_products.
How it works
FunctionRole
loadPriorityCanonicals() Loads all canonicals WHERE is_match_priority=1 AND brand_slots IS NOT NULL. Pre-compiles slot regex patterns once per crawl run — not per deal.
matchesCanonical(deal, canon) Checks: all brand_slots patterns match the normalised name AND all base_product_slots patterns match AND weight is within ±10%. Returns true only if ALL conditions pass.
autoMapDeals(storeDeals) For each unmatched deal, iterates priority canonicals, calls matchesCanonical. On match: writes deal_mappings row with match_method='slot_match', confidence=0.85.
Concrete example
// canonical_products row canonical_name: "Heera Soan Papdi 500g" brand_slots: [["heera"]] base_product_slots: [["soan"],["papdi"]] weight_value: 500 // grams is_match_priority: 1 // incoming deal name: "HEERA SOAN PAPDI 500GMS" // normalised → "heera soan papdi 500g" // matchesCanonical checks: // ✓ "heera" matches brand_slots[0] // ✓ "soan" matches base_product_slots[0] // ✓ "papdi" matches base_product_slots[1] // ✓ 500g weight within ±10% of canonical 500g // → MAPPED with confidence=0.85
Important: canonical_id sync

autoMapDeals() writes deal_mappings rows but does NOT update deals.canonical_id. That sync only happens when upsertDealMapping() is called from the canonicalizer in Pass B. A slot-matched deal gets its deals.canonical_id set during Phase 4 of the same crawl run.

Pass B — Fuzzy Canonicalization
Runs after all stores are scraped. Processes all unmapped active deals via canonicalizeDeals(unmappedOnly=true).
Three-outcome decision tree
normalise(deal.name) │ ├─ exact match in canonical_products? │ └─ YES → map, confidence=1.0, done │ ├─ fuzzy match ≥ 0.90? │ └─ YES → auto-map, write deal_mappings, │ update deals.canonical_id, done │ └─ NO match / confidence < 0.90 └─ INSERT into entity_resolution_queue (status='pending', for admin review)
Normalisation

normaliser.js lower-cases, removes punctuation, expands common abbreviations (e.g. gms → g, kgs → kg), strips stop words, and strips weight tokens before fuzzy string comparison. Canonicals are also normalised the same way before comparison, so the comparison is always normalised↔normalised.

The 0.90 threshold

Below 0.90 the match is considered ambiguous. A suggested canonical is still recorded alongside the raw/normalised name in entity_resolution_queue so an admin can confirm or reject without looking the product up from scratch.

canonical_products — The Entity Resolution Hub
A store-agnostic product identity. One canonical = one real-world product regardless of which store sells it or how they name it.
What is a canonical?

A canonical product is a normalised product identity that multiple store deals can be linked to via deal_mappings. It answers: "Is the Heera Basmati 5kg at Jamoona the same product as HEERA BASMATI RICE 5KG at Dookan?" — yes, one canonical, two deals.

Currently ~300+ canonical identities in the database.

Key fields

brand_slotsJSONNested array of token patterns for brand matching: [["heera"]]
base_product_slotsJSONCore product tokens: [["basmati"],["rice"]]
type_slotsJSONVariant qualifier tokens (e.g. [["chakki"]] for chakki atta)

Real Savings — How It Works
Computes whether a current sale price is genuinely low relative to historical norms — not just the store's own stated discount.
Computation steps
StepDetail
1. Load historyQuery deal_price_history for last 90 days, is_deal=0 rows (normal-price days), joined through deal_mappings to group by canonical_id
2. Qualify baselineRequire ≥3 observations. Canonical grouping pools all pack sizes of the same brand+product across all stores into one reference price
3. Compute medianMedian of normal_price_per_kg (= COALESCE(original_price, sale_price) × price_per_kg / sale_price) as baseline
4. CompareCurrent deal's price_per_kg vs baseline → real_discount_pct = (baseline − current) / baseline × 100
5. BadgeApply thresholds (see below). Two suppression rules filter out noise.
Rating thresholds
RatingThresholdBadge
Great dealreal_discount_pct ≥ 25%Great
Good dealreal_discount_pct ≥ 15%Good
Low savingreal_discount_pct ≥ 5%Low
Not shown< 5% or suppressedNone
Badge suppression rules

Rule 1: Suppress if computed real savings > store's stated discount_percent. Distrusts data that claims more saving than the store itself states.

Rule 2: Suppress if |real savings − stated discount| < 5pp. Badge adds no meaningful information when both values are nearly identical.

Fake-deal detection

Deals where the price_per_kg is implausibly low (below FAKE_DEAL_THRESHOLD_PP) are flagged. The constant is defined in real-savings.js and the flag is surfaced in the admin dashboard.

Fallback layer

When no canonical history exists (new product, <3 observations), Layer 2 falls back to the store's own stated original_price vs sale_price. This is a weaker signal — it trusts the store's own data — so it is displayed differently in the UI.

Product Replacements — Compare Stores
When a deal is out of stock, the replacement engine finds the best alternatives within the same store, ranked by tier.
API endpoints
GET /api/v1/deals/replacements ?canonical_id={id} &store_id={id} &deal_id={id} // optional; source weight falls back to canonical if omitted GET /api/v1/deals/same-product-other-stores ?canonical_id={id} &store_id={id} // cross-store alternatives via base_key + category SQL join
Four-tier classification
TierNameRelevanceLogicExample
T1 same_pack 1.0 Same brand + exact base_product_slots match + different weight. Sorted weight ascending. Heera Soan Papdi 250g as alternative to 500g (same brand+product, different size)
T2 same_spec 0.85 Cross-brand, same base product. Primary: exact base_product_slots set match. Fallback: catalog base_key equality — handles Hindi/English term divergence (e.g. "Mung Sabut Whole" ↔ "TRS Mung Beans" both → "moong dal yellow"). Natco Soan Papdi 500g as alternative to Heera; Mung Sabut 500g as alternative to TRS Mung Beans
T3 same_brand 0.65 Same brand + same product_group_id (base_key equality or slot-subset check). Sorted discount% desc then price asc. Heera Gulab Jamun Mix as alternative when no Soan Papdi alternatives exist
T4 same_category 0.4 Fallback only — emitted when T1+T2+T3 are ALL empty. Displayed as collapsed CTA pill in UI. Any Snacks & Sweets deal in-store when no brand/spec match found
